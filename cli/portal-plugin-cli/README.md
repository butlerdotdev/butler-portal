# @butlerlabs/portal-plugin-cli

Butler Portal plugin CLI. A thin, honest wrapper over
[@red-hat-developer-hub/cli](https://www.npmjs.com/package/@red-hat-developer-hub/cli)
for authoring dynamic frontend plugins that load into Butler Portal at
runtime.

The portal runtime (`@module-federation/runtime` host inside
`packages/app`) loads a plugin's bundle from an OCI artifact or HTTPS
tarball, reads the plugin's `dynamicPluginsExports` declaration, and
mounts each declared route at the host's URL. The plugin side of that
contract is generated by `rhdh-cli plugin export`. This wrapper exists
so the test plugin scaffold, the examples directory, and the adopter
docs all reference a Butler-stable command surface
(`butler-portal-plugin`) regardless of how the underlying CLI evolves.

## Install

```sh
npm install --save-dev @butlerlabs/portal-plugin-cli
```

or

```sh
yarn add --dev @butlerlabs/portal-plugin-cli
```

The package declares `@red-hat-developer-hub/cli` as a direct
dependency; an adopter who wants to inspect or pin the underlying
toolchain can see exactly which rhdh-cli version their plugin builds
against.

## Use

Every command is forwarded verbatim to the underlying rhdh-cli binary.
The wrapper's only added behavior is a one-line banner identifying its
version and the rhdh-cli version it pins, plus exit-code propagation.

```sh
# Build the dynamic-plugin artifact (the most common command):
npx butler-portal-plugin plugin export --clean --no-install
```

Everything `rhdh-cli` accepts, `butler-portal-plugin` accepts. The
subcommands and their flags are documented at the
[rhdh-cli repo](https://github.com/redhat-developer/rhdh).

## What `plugin export` produces

A `dist-dynamic/` directory containing:

* `dist/mf-manifest.json` -- the Module Federation v2 manifest the
  portal's runtime reads.
* `dist/remoteEntry.js` plus per-chunk static assets -- the federated
  bundle the runtime fetches.
* `dist/.config-schema.json` (if your plugin declares a config
  schema) -- merged into Backstage's app-config validation at portal
  boot.

Pack `dist-dynamic/` as `package/` inside a `.tgz` tarball, compute
the `sha512` SRI integrity, and push the result to an OCI registry
or HTTPS endpoint. The portal's
[chart](../../charts/butler-portal/) `dynamicPlugins.plugins[]` block
references it by URL + integrity. See the adopter docs for the full
publish flow.

## Host runtime contract

The host provides the following packages as shared singletons. Your
plugin's `mf-manifest.json` declares them in its `shared` block (the
rhdh-cli export handles this when the packages are direct deps of
your plugin):

* `react` (18.x)
* `react-dom` (18.x)
* `react-router-dom` (6.x)
* `@material-ui/core/styles` (4.12.x)
* `@material-ui/styles` (4.11.x)

Material-UI v4 splits its styling primitives across two packages.
Declaring only `@material-ui/core/styles` and forgetting
`@material-ui/styles` produces `TypeError: theme.spacing is not a
function` at first render. Declare both.

## Why a wrapper instead of telling adopters to use rhdh-cli directly

Three reasons:

1. **Stable command surface in the docs.** A Butler Portal docs page
   that says `butler-portal-plugin plugin export ...` does not need
   to be rewritten if rhdh-cli changes its binary name.
2. **Seam for Butler-Portal-specific behavior.** When (if) the runtime
   contract grows divergent from rhdh-cli's defaults, the wrapper
   becomes the place where Butler-specific transforms or validations
   land without breaking adopter scripts.
3. **Honest pinning.** The package.json shows exactly which rhdh-cli
   version any given wrapper release builds against. Adopters who
   need to investigate a rhdh-cli regression have a single field to
   read.
